# P8 — 육성 계획 저장·복원 및 출력 검증

기준일: 2026-11-05. **P8 구현·검증 완료.** 실제 ID를 사용하는 테스트 인자 소유·백인자 기록은 사용자가 입력한 상황을 합성한 것으로, 한국 서버에서 관측한 완성 인자나 새 게임 규칙의 증거가 아니다. 저장 전후 입력·소유 관계 일치, 실제 다운로드 파일과 시각 검수, 기존 계산 회귀를 근거로 완료를 판정했다.

## 1. 저장 파일 스키마와 버전 관리 정책

`src/domain/saved-plan.ts`의 독립 P8 어댑터를 사용한다. 기존 P2·P7와 원본 게임 계약은 수정하지 않는다.

- `contract: uma-saved-plan`, `schemaVersion: 1`, `formatVersion: 1`
- 소문자 canonical UUID `planId`, 이름, 생성·수정 ISO 날짜, 생성 앱 버전
- `snapshotIds.reference/p3/p5`는 저장 형식과 별개인 게임 데이터 snapshot ID
- `inputs`는 사용자 입력이며 `resultSnapshot`은 선택적인 과거 결과 참고 자료

미래 저장 버전은 추측 변환하지 않고 거부한다. V1 외의 과거 P8 저장 형식은 아직 존재하지 않으므로 실제 과거 버전 마이그레이션은 제공하지 않는다. 명시적인 버전 분기 지점과 가져오기 원문 `rawBackup`을 유지한다.

| P7 기록 | 노드별 보유/제작 목표, 별수 null/1/2/3, 미입력/부분/확인 상태, 표시 참고 이름, 분류 근거 |

검색 문자열, 접기/펼치기, 로딩·Worker 실행 상태 등 조회용 상태는 입력 저장 대상에서 제외한다. 인자작 추천 6장은 실제 사용자 선택 UI가 없으므로 `resultSnapshot.cards`에 참고 자료로만 보관한다. 전체 게임 DB는 포함하지 않는다.

## 3. 인자 개체 식별자 설계

`nodeId`, `ownerCostumeId`, `factorInstanceId`, `planId`를 분리했다. UUID는 Web Crypto의 독립 난수를 사용하며 이름·스킬 목록·시각의 해시로 생성하지 않는다. 동일 노드의 기록 수정은 UUID를 유지하고, 다른 실물 교체는 새 UUID를 요구한다. 계획 복제는 planId만 바꾸고 동일 물리 인자의 UUID를 유지한다.

한 계획 내 서로 다른 노드가 같은 UUID를 공유하면 거부한다. UUID의 대소문자 차이로 같은 식별자를 두 개처럼 등록하지 않도록 canonical 소문자 표기를 요구한다.

## 4. 동일 캐릭터·의상의 복수 인자 관리 사례

단위 테스트는 같은 의상 `100901`을 31개 소유 노드에 배치해 독립 UUID 31개를 검사한다. 실제 DB 기반 JSON 예시에서는 증조·고조의 같은 의상을 여러 노드에 배치하되 개체 UUID와 백인자를 분리했다. 의상 동일성으로 보유 기록을 합치지 않는다.

`data/local/p8-persistence/seven-node-example.json`과 `31-node-example.json`을 보존했다. 후자는 글로벌 추천 요청을 저장하며, 전자는 선택 부모 및 노드별 모드의 보존도 검사한다.

## 5. 혈통 변경·잠금·복원 안전성

- 명시적 교체는 선택 노드의 백인자·로컬 목표·적인자를 비우고 새 UUID를 부여한다. 다른 노드의 기록과 기존 조상 그래프는 유지한다.
- 교체 노드와 직접 연결된 아래 세대 소유자의 혈통 확인을 보류한다. 부모 집합 재배치나 알려진 부모 개체의 변경도 확인이 필요하다.
- 첫 작성에서 빈 슬롯에 처음 소유자를 선택하는 것은 과거 실물 교체로 취급하지 않는다. 본육성→부모→조부의 순차 7인 입력 각 단계가 확인 강요 없이 유지되는 엔진 검사를 추가했다.
- 선택을 지웠다 같은 의상을 재선택해도 이전 혈통이 자동 확인되지 않는다. 선택 해제 시 null 소유자·미확인 상태의 비활성 UUID 이력을 보존하고, 재선택 시 새 UUID를 만든다.
- 잠금된 노드 및 잠긴 아래 세대가 보호하는 조상은 교체할 수 없다. P8 어댑터에 직접 변조한 보호 노드도 거부한다.
- 미완성 날짜 입력 중 계보 수정은 보존하되, 미완성 입력의 저장/복원은 엄격 검증에서 거부한다.

복원은 검증과 요약 후 App의 단일 `workspace` 교체로 적용한다. epoch를 즉시 올려 이전 컴포넌트의 결과 콜백을 거부하고 Worker·실행 토큰·계산 미리보기를 무효화한다. PNG도 입력 변경과 컴포넌트 해제 시 비동기 출력을 차단한다. PC·모바일에서 실행 중 Worker가 종료되고 이전 결과가 다시 나타나지 않는 것을 검증했다.

첫 출력 E2E에서 부모A→B 전환 후 이전 UUID 표시가 DOM에 남는 결함을 발견했다. 인자 개체 편집기와 백인자 편집기에 같은 React key를 사용한 것이 원인이며, 각각 `instance:nodeId` / `skills:nodeId`로 분리했다. 저장 바이트가 바뀌지 않더라도 잘못된 소유자 표시가 가능한 결함으로 취급해 검사를 중단하고 수정했다. 같은 의상 두 인자의 UUID 분리·편집 유지·교체 후 기록 제거·혈통 재확인·잠금 시나리오를 PC·모바일에서 다시 통과했다.

## 6. 복수 계획 저장 및 전환 사례

`createPlanRepository`는 여러 계획과 마지막 계획 포인터를 하나의 localStorage 키 `uma.p8.saved-plans.v1`에 기록한다. 덮어쓰기는 명시적 옵션이 필요하며 UI는 삭제·덮어쓰기 확인과 복원 미리보기를 제공한다. 이름 변경·복제·삭제가 다른 계획 입력을 수정하지 않는 단위 검사를 수행했다.

실제 DB CLI는 두 계획을 저장하고 새 repository 인스턴스로 동일 데이터를 다시 읽었다. 이것은 저장 어댑터 검증이며 실제 브라우저 새로고침 검사의 대체 증거로 취급하지 않는다. 마지막 계획은 자동 적용 대신 사용자가 검증 요약을 확인해 복원할 수 있도록 구현했다.

별도의 실제 브라우저 검사에서는 31개 슬롯을 직접 입력해 조부 배치6·잠금2개·적인자25개·백인자3기록·노드/전역 목표·본육성6장과 서로 다른 돌파·보유3장/대여금지·미래시 모드를 저장했다. 새로고침 후 마지막 계획 미리보기에서 명시적으로 복원했고, PC·모바일 각각 저장 전후 전체 입력과 메타데이터 및 JSON SHA-256까지 동일했다. 같은 의상 `100101`의 깊은 조상24개도 각각 다른 UUID24개로 유지됐다. 독립 검토 결과는 `.preview/p8-artifacts/persistence-roundtrip.json`이다.

미저장 알림과 `beforeunload` 보호는 첫 저장 이전의 실제 입력부터 적용한다. 소스 로딩으로 채워지는 기본 대회·시나리오와 단순 선택 노드 조회는 입력 수정으로 세지 않는다. 사용자 설정을 초기 기준으로 뒤늦게 바꾸지 않도록 최초 입력 사본과 소스 기본값을 분리했다.

## 7. JSON 파일 내보내기·가져오기 검증

크기 한도는 UTF-8 기준 2MiB다. JSON 객체의 중복 키, `__proto__`·`prototype`·`constructor`, 과도한 중첩, 손상된 JSON, 알 수 없는 필드를 거부한다. `eval`이나 동적 코드 실행·외부 업로드를 사용하지 않는다.

노드 수, 순환/공유/끊어진 부모, UUID 충돌, 노드/소유 의상 불일치, 별수·우선순위·날짜, 카드 중복과 버전을 검증했다. ID를 표시 이름으로 매핑하지 않는다. 가져오기 실패 시 원문 백업과 오류를 보존하며 작업 입력은 적용하지 않는다. 동일 planId의 가져오기는 명시적 덮어쓰기 또는 새 계획 복제로 처리하는 UI다.

실제 DB CLI 31인 JSON은 **37,531바이트**이며 내보내기→미리보기→복원 입력이 깊은 비교에서 완전히 동일했다. 별도의 UI 직접 입력 예시는 PC·모바일 각각 **18,425바이트**이며 실제 다운로드 후 새로고침·명시적 복원을 거친 파일 전체가 저장 전과 동일했다. 두 예시는 사용자 입력 내용이 서로 다르며 모두 전체 게임DB를 포함하지 않는다. 브라우저 파일 선택·다운로드·동일 planId 덮어쓰기/사본 선택·취소도 통과했다.

## 8. 게임 DB 버전 변경 시 복원 정책

스냅샷 ID가 달라도 모든 canonical ID가 남아 있으면 입력을 유지해 복원할 수 있으며 재계산 안내를 표시한다. 캐릭터·스킬·서포트·대회·시나리오 ID가 누락되면 후보 계획과 원문을 보존하되 적용을 차단한다. 이름 유사 매핑이나 조용한 삭제는 하지 않는다.

금색·고유·진화·비canonical 목표를 일반 백인자로 임의 변환하지 않는다. 현재 소스가 백인자 자격을 검증하지 않았는데 가져온 파일이 `verified`라고 주장하는 경우도 차단한다. 실제 백인자 생성 자격 인증 자료는 여전히 0건이다.

## 9. 계획 및 서포트 편성 비교 결과

구현은 같은 현재 DB로 계보 상성·적성과 추천 요청을 재구성하고 Worker에서 새 추천을 계산한다. 과거 resultSnapshot 점수·스킬 합집합을 현재 양립 수급 근거로 사용하지 않는다. 대회·각질·시나리오·출시/소유 환경이 다르면 조건 차이를 표시하고 직접 우열 판정을 하지 않는다. 스킬 및 검증된 수급 경로의 전체 차집합을 비교한다.

실제 CLI는 저장 입력에서 `buildSavedPlanRecommendationRequest`로 복원 전후 요청을 각각 만들고 완전 일치를 확인했다. 아래 실제 6장을 현재 엔진으로 양립 이벤트 계획까지 다시 평가해 같은 결과를 얻었다.

| 편성 | 결과 |
|---|---|
| 30175 / 30113 / 30140 / 10126 / 30226 / 30107 | 정성 374 + 사용자 8 = 382, 양립 목표 48, 녹딱 8 |

검사는 지정한 실제 6장의 동등성 검증이며 전체 후보 전역 최적성 인증이 아니다. PC·모바일 출력 E2E에서도 저장 A/B를 현재 데이터로 비교했다. 두 계획의 새 추천은 같은 B편성374+8=382 / 양립48 / 녹8로 같았다. 저장 당시 A6장 자체는374+8=382 / 양립48 / 녹9, B6장은374+8=382 / 양립48 / 녹8로 별도 재평가했다. 저장 캐시에는 의도적으로 스킬2개만 두었으나 현재48개 목표와 선택 이벤트 계획을 다시 표시해 과거 합집합을 재사용하지 않는 것을 확인했다.

계보 비교에서는 부모A의 더트3성→잔디1성, 실제 보유 터다지기2성→1성, 서로 다른 UUID·노드 목표·혈통 확인 차이를 이름/ID와 함께 표시했다. B의 계보 계산은 혈통 재확인으로 보류하면서 계보 의존성을 쓰지 않는 전역 스킬 추천을 분리했다. 추입 계획으로 비교 대상을 바꾸면 `서로 다른 조건의 참고 비교 · 점수로 우열을 판정하지 않습니다`를 표시했다. 실제 파일과 비교 화면은 `.preview/p8-artifacts/{desktop,mobile}-comparison-{a,b}.json`, `*-comparison-current.txt`, `*-comparison.png`에 보존했다.

기존 화면과 비교 요청의 시나리오 선택도 일치시켰다. P5 컨텍스트에서 저장된 시나리오가 가용하지 않으면 원래 입력을 보존한 채 기존 화면과 같은 첫 가용 시나리오로 계산한다. 실제 자료 발췌 회귀에서 시나리오13 입력 유지, 미래시 OFF 시 유효 시나리오1 / ON 시13을 확인했다.

## 10. 실제 PNG 출력 결과 및 시각 검수

코드에는 7인 요약, 31인 전체 대형 이미지, 현재 6장 추천 출력용 텍스트·Canvas 레이아웃이 구현되어 있다. 출력 중 새 게임 계산을 호출하지 않고 화면의 검증된 현재 결과와 입력 서명을 사용한다. 외부 캐릭터 아트를 내려받지 않고 의상 명칭·ID로 대체한다.

PC와 모바일 에뮬레이션에서 실제 다운로드한 아래6개 PNG를 모두 파일로 열어 시각 검수했다. 한국어·일본어 혼합 명칭과 ○/◎/★, 긴 의상명·스킬·이벤트 선택 ID가 줄바꿈되며 빈 화면·좌우 잘림·하단 누락이 없었다. 31인 파일은 고조16 및 마지막 ancestor_30 기록까지 표시했다. 외부 이미지가 없어 명칭과 의상/서포트 ID가 일치하는 대체 레이아웃이다.

## 14. 실패 처리·남은 한계·P9 이관

검증한 실패 사례는 쿼터 초과, 저장소 접근 거부, 손상 저장소, 손상 파일, 미래 버전, ID 누락, 소유 충돌 및 그래프 오류다. 저장 실패를 성공으로 표시하지 않고 기존 저장 바이트를 유지한다. 저장소 전체를 하나의 키로 기록하며 읽을 수 없는 크기의 저장소를 새로 쓰지 않도록 한도를 적용했다. JSON 백업은 브라우저 저장 성공과 분리했다.

미확인 백인자 생성 자격·한국 실측·정량 마신 데이터는 새로 인증하지 않는다. 다중 탭의 동시 수정을 병합하는 기능, 인자 라이브러리 자동 병합, 계정/서버/클라우드, PDF·이미지 편집기는 범위 밖이다. 실제 정적 배포와 전체 데이터 로딩 검증은 P9로 이관한다.

저장·File/Blob·Canvas는 브라우저 기본 API와 주입형 저장 어댑터이며 개발 서버의 쓰기 API를 사용하지 않는다. 현재 게임 자료 로더는 기존 개발 경로를 유지한다. 게임ID 대조 자료가 없으면 복원/비교는 차단하되 저장 목록 조회와 현재 입력 JSON 백업은 가능하다. 프로덕션 전체DB 공급은 P9에서 검증한다. 매우 큰 기록으로 Canvas 높이32,760px/면적 한도를 넘으면 잘린 그림을 만들지 않고 오류를 표시한다. JSON 백업은 별도로 사용할 수 있다. Quota/SecurityError 검사는 API 오류 주입이며 실제 모든 비공개 모드의 인증은 아니다.

보존 산출물: `data/local/p8-persistence.validation.json`, `data/local/p8-persistence/seven-node-example.json`, `data/local/p8-persistence/31-node-example.json`, `.preview/p8-artifacts/`의 실제 PNG/JSON/비교 화면·`persistence-roundtrip.json`·SHA manifest. 단순 테스트 수뿐 아니라 실제 입력과 소유 관계의 저장 전후 일치 및 실제 파일 시각 검수를 확인했으며, 해결하지 않은 소유 관계 오류는 발견되지 않았다.
