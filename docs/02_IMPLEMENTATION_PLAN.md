# 개발 계획 · Codex 작업 분할 v1.0

**원칙:** 화면을 만들기 전에 DB 전체를 완성할 필요가 없다. **검증된 소규모 샘플 데이터로 각 계산 엔진의 정확성을 먼저 입증**하고 수집 범위를 확장한다.

## 1. 기술안 — 구현 선택(확정 요구 아님)

- 프런트: TypeScript + React + Vite (또는 동등한 정적 배포 스택). 모바일/PC 반응형 CSS.
- 엔진: `src/engine/`의 순수 TypeScript 함수, 프런트 UI와 분리. API 호출 및 AI 의존성 없음.
- 데이터: 타입/스키마 검증된 버전드 JSON 스냅샷. 빌드 전 검증 스크립트.
- 저장: localStorage(작은 설정), IndexedDB(설계 다수), JSON 파일 내보내기/가져오기. URL 공유는 후속 선택 구현.
- 배포: GitHub Pages/Cloudflare Pages 중 한 곳, 정적 프런트. 데이터 수집은 로컬 또는 GitHub Actions 사전 빌드 시 수행.
- 테스트: Vitest(unit); Playwright(E2E), Zod(or JSON Schema) 데이터 유효성, ESLint/TypeScript/빌드 게이트.
- 저작권: 외부 오픈소스의 코드를 참조로 읽는 것과 복제하는 것을 구분. 이용조건 불명확한 코드·게임 아트는 복제 금지.

## 3. 작업 단위와 완료 조건

### P0: 개발 골격과 데이터 계약

**작업:** 프로젝트 초기화, 데이터 타입/검증, ID 모델, 출처 메타데이터, 날짜 필터의 최소 구현, 가상 fixture, 테스트 도구.

- `character_base_id` vs `costume_id` 구분; 하나의 캐릭터에 여러 의상/능력치 및 이미지 매칭.
- 한국/일본 출시일·추정/확정 상태, 버전/출처 ID 정의.
- 시간대 `Asia/Seoul` 및 `tournament_start` 기준 필터 구현.
- 팩의 스키마 오류, 중복 ID, 미존재 외래키, 출시일 역전 검사.

**완료:** 가상의 출시일 테스트 4개 및 데이터 무결성 테스트 통과, UI 없이 함수 호출 가능.

### P1: 7인 계보 핵심 — 첫 번째 실제 동작 시연

**작업:** 샘플 캐릭터 20~50개+상성 검증 샘플로 7슬롯 UI, 상성 계산, 이름 검색, 적성/빨간 인자 입력, 후보 추천.

- **G1 우승 가산치 추가 금지**.
- 계산 엔진과 UI 분리. 기본 상성 출처/버전 표시.
- 부모 P1/P2 고정, 조부 4명 6가지 묶음 배치 테스트.
- 7인 트리를 데스크톱/모바일로 사용 가능하게 구현.

**완료:** 공식/검증된 예제 케이스에서 기본 상성 값 비교 통과. 슬롯 교체 시 즉시 갱신, 중복 배치 없음.

### P2: 31인 자동 빨간 인자 배분

**작업:** 31 슬롯 도메인 트리, 세대별 적성 영향 계산, 목표 로테이션 프로필, 고조/증조 빨간 인자 자동 배분, 유전자 목표 스위치.

- 조부모 인자 생성 가능한 A 적성, 인자작 로테이션 소화 조건 준수.
- 우선순위: 제약 충족 → 12성(무손실 가능하면) → 6성 대안 → 혈통 집중 우대 → 기본 상성 비교.
- 31명 전부 사용자에게 수동 지정하도록 요구하지 않는다.
- 동일 별수/목표인 경우 집중형을 우대하고, 왜 그렇게 추천했는지 설명.
- 성수 조건을 실제 게임 검증 케이스로 고정한 후 활성화.

**완료:** 6/12성·집중/분산·부모/조부 범위·적성 부족 경계 사례 통과. 31인 모바일 세대별 펼침 정상.

### P3: 대회별 스킬·본육성 덱 데이터

**작업:** 대회 테이블, skill ID 매핑, 코스 유효성, 녹딱 우대, 본육성 서포트의 힌트 수급 경로, 우선순위 조절.

- 기본: 대회×각질 공통 유효 스킬 목록.
- 마신/유효율이 검증된 스킬만 수치 표시, 나머지는 정성 등급.
- 본육성 카드가 주는 힌트도 백인자 후보에서 완전 제거하지 않음.
- 금색→하위 백인자 관련 데이터는 별도 관계로 관리.

**완료:** 한 가지 한국 서버 대회×각질 실제 공략 사례와 비교 가능한 평가표. 데이터 출처/검증 상태 표시.

### P4: 6장 서포트 추천 엔진

**작업:** 후보 카드 압축 → 링크 카드 우선 고려 → 6장 조합 생성 → 고유 유효 스킬 합집합 비교 → 세 성향별 추천 → 근거 설명.

- 이미 있는 힌트만 제공하는 카드의 **신규 스킬 기여는 0**.
- SR 도배만 경미하게 경고. 특정 스탯/완주율 예측·인자화 확률 합산 하지 않음.
- 보유 카드 및 돌파 필터; 렌탈 슬롯 표시.
- 6장 조합 순위는 **단일 카드 고정점수의 상위 6개 선택 방식이 아님**.
- 대체안은 실제 신규 스킬 목표에 차이가 있을 때만 제시.

**완료:** 동일 데이터/조건에서 결정론적 결과, 신규 W 카드가 중복만 있는 카드보다 적절히 선택, 추천 이유 출력.

### P5: 종마 후보·저장/비교/이미지 내보내기

**작업:** 서포트에서 빠진 스킬→종마 캐릭터 후보 탐색; 계보/편성 저장, JSON 입출력, 브라우저 저장, PNG 결과 다운로드.

- 종마 후보가 인자를 이미 보유한 것처럼 오해되는 문구 금지.
- 저장 데이터 `schema_version`, `dataset_version`, `as_of` 포함.
- 이미지 없는 캐릭터도 텍스트/실루엣으로 정상 렌더.

**완료:** 공유 전 내보내기 파일로 복구, 스키마 버전 테스트, 7인/31인/6장 결과 PNG 출력.

### P6: 한국 출시일 갱신 파이프라인과 배포

**작업:** 데이터 수집 스크립트, 한국 출시일 관리자 파일, 타임라인 정합성 검증, 빌드/배포 검증, 경량 정적 운영.

- 공식 확정 vs 미래시 추정 필드 분리.
- 데이터가 새로 들어오면 기존 아이템 ID와 카드/스킬 관계 파손 검증.
- 한국 출시 패치와 일본 최신 패치 효과를 같은 시점으로 착각하지 않음.
- 이용권한 확인 전 이미지는 fallback로 유지.

**완료:** 출시일 하나를 변경한 데이터 팩에서 해당 대회 기준 추천 후보가 자동 바뀌는 통합 테스트 통과.

## 4. 구현에서 가장 주의할 5개 함정

1. **'범용'의 뜻 변경 금지:** 선택 대회×각질에서 여러 캐릭터가 공유할 스킬이다. 다른 이벤트 재활용 점수 아님.
2. **'기본 상성'에 G1 추가 금지:** 중상작은 사용자가 실제 인자작에서 할 일이다.
3. **'체급' 과설계 금지:** 카드 조합 훈련 시뮬레이터 만들지 않는다. SR 도배만 가벼운 경고.
4. **'출시 여부' 현재 고정 금지:** 미래 대회 선택 시 그 대회 시작일을 기준으로 평가. 예측 데이터 미래시 명시.
5. **'스킬 조합 최종 전개'를 인자작에 강요 금지:** 핀포인트가 아닌 대회·각질 공통 목표 스킬을 넓게 취득한다.

## 5. 권장 성능 목표 — 구현 선택

- 7인 UI 반응: 체감 즉시, 로컬 계산.
- 6장 조합 탐색: 후보 압축 및 조합 상한 설정, Web Worker 사용 가능(필수 아님). 결과와 함께 후보 수·최적화 조건 기록.
- 31인 화면: lazy 펼침, 이미지 lazy-loading.
- 테스트 우선순위: **정답이 검증된 fixture**가 없는 고도 최적화는 구현하지 않음.
- 성능 최적화 전에 정확성을 측정하고, 동일 입력·데이터 버전으로 결과 재현 가능하게 유지.

## 6. Codex 작업 수칙

- 한 번에 P0~P6을 전부 구현하지 말 것. P0→P1→P2 순서대로 결과를 실제 테스트로 검증.
- 데이터 출처가 확보되지 않으면 검증된 소규모 fixture를 쓰고 임의 '실제 상성' 숫자를 채우지 말 것.
- 기능 추가 전 `01_REQUIREMENTS.md`의 ID와 대응 수용시험을 확인.
- 소스 데이터 수집·이미지 재배포가 미허용 상태면 스크래핑이나 게임 이미지 사용을 강행하지 말 것.
- 빌드 결과 보고에 **실행한 테스트·통과 여부·미구현 사항**을 명확히 기록.
- 작업 중 발견한 애매한 기술 선택은 `docs/DECISIONS.md`에 근거와 함께 기록; 이미 확정한 사용자 의도를 재해석하지 말 것.
